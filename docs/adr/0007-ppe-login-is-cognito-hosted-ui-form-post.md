# PPE login is a Cognito Hosted UI form POST, driven directly over HTTP

The exact login mechanics were unknown going into #1 (see `openspec/changes/ppe-authentication/design.md`, Open Questions). Inspecting the real, unauthenticated redirect chain from `https://ppe.data.europa.eu/` (confirmed live against PPE, same technique ADR-0003 used) showed: PPE runs the "cloudfront-authorization-at-edge" pattern — an unauthenticated request is 307-redirected to a Cognito `/oauth2/authorize` URL (PKCE `code_challenge`/`state` generated and tracked server-side via `spa-auth-edge-*` cookies on `ppe.data.europa.eu`, not by the client), which itself redirects to Cognito's Hosted UI `/login` page. That page is a plain server-rendered HTML form (`name="cognitoSignInForm"`) POSTing back to its own URL with fields `_csrf` (a token embedded in the page, not just the `XSRF-TOKEN` cookie — read it from the HTML), `username`, `password`, and `signInSubmitButton`. A successful POST redirects through `https://ppe.data.europa.eu/_identities/parseauth` (the edge Lambda exchanging the code using its own stored PKCE verifier) back to the originally requested page, with the browser now holding the final session cookies.

Consequently, the login flow is drivable with plain HTTP (`requests.Session`, no browser automation): GET the base URL, follow redirects to the Hosted UI login page, parse the CSRF token and form action out of the returned HTML, POST credentials, and check whether the final URL still lands on `/login` (failure) or back on the app (success). No JS execution or headless browser is needed — the `design.md` fallback (Playwright) is not required.
